### 2.3 总体策略

> **校赛**：聚焦"双引擎评审 → 证据链 → 一键修复"演示主线（创新点 1、创新点 2 的 1 条规则、创新点 4 的 1 类修复），其余延后。
> **省赛**：在此基础补齐全部创新点功能 + 五件套材料 + 量化对比实验数据。

**校赛 MVP 功能范围（必做项）：**

1. IDEA 插件可安装运行（Gradle `runIde` 或 ZIP 安装）。
2. 编辑器右键菜单"智能代码评审"入口。
3. **规则引擎**（PMD）内置 3~5 条规则，对当前 Java 文件输出问题清单。
4. **大模型评审**：调用 API 做语义评审，输出结构化意见（含证据链：问题行号 + 问题原因）。
5. **统一结果面板**：合并三路评审结果（PMD 规则 / 大模型 / PSI 框架分析），标注来源、严重级别、文件行号。
6. **点击定位**：点击结果跳转至对应代码行并高亮。
7. **一键修复**：至少 1 类问题支持"生成修复补丁 → Diff 预览 → 应用"。
8. **亮点功能**：Spring `@Transactional` 事务失效检测规则（校赛 1 条，答辩核心展示点，见 3.2）。

**省赛扩展（校赛后逐步实现）：** SpotBugs 集成、更多框架感知规则（Bean 作用域、循环依赖）、Maven 依赖安全扫描、量化对比实验、UI 打磨。

## 三、创新点可行性评估（指导老师意见）

### 3.1 逐条评估

#### 创新点 1：规则引擎 + 大模型"双引擎"混合评审架构
- **结论：可行，保留为核心卖点；"融合机制"需深入阐述，并有数据支撑。**
- 技术路径可行：PMD/SpotBugs 均提供可编程 API；LLM 结构化输出为成熟方案。
- **风险**：评委会质疑"规则 + LLM 组合已有先例"（SonarQube、Snyk Code 及学术界混合方案）。仅表述"两者都用"会削弱创新性。
- **答辩口径**：将架构阐述为**分级流水线 + 双向增强**，而非并列展示：
  1. 规则引擎先行扫描（确定性、零成本、毫秒级），产出精确证据链；
  2. LLM 处理规则覆盖不到的语义/上下文问题（规则盲区）；
  3. **LLM 对规则命中项做误报复核**（降低误报）；
  4. **规则结果作为 LLM 的上下文约束注入 Prompt**，抑制大模型幻觉。
  → 一句话表述："确定性问题用确定性方法，语义问题用推理方法，两者互相校正。"
- **数据支撑**：省赛前用 20~30 个含已知缺陷的样本做三组对比（纯规则 / 纯 LLM / 混合）的精确率、召回率、误报率，图表化后放入 PPT，作为回应质疑的关键材料。

#### 创新点 2：面向 Java 企业开发生态的框架感知评审
- **结论：可行，为四个创新点中差异化最强项，作为答辩重点。**
- 技术路径：IntelliJ PSI 语法树 + Inspection API，识别 Spring 注解语义后做结构级分析。
- 典型可检测缺陷（按实现优先级）：
  1. `@Transactional` 受检异常不回滚（未配 `rollbackFor`）——**校赛仅实现此条的完整演示**；
  2. `@Transactional` 同类内部方法调用（this 调用绕过代理，事务失效）；
  3. `@Transactional` 标注在非 public 方法上（AOP 代理限制）；
  4. Bean 作用域误用（省赛）；
  5. 循环依赖检测（省赛）。
- **差异化论证**（答辩必备）：PMD/SonarQube 规则集无法覆盖"跨方法、跨 Bean 的框架语义问题"；通用 AI 助手不主动做项目级框架结构分析。**"结构级 + 框架语义"是与通用代码助手的根本分界。**
- **风险**：Spring 语义索引（Bean 与事务注解识别、代理边界判断）工作量较大；省赛阶段限定"3~5 条高置信规则"，不做大而全。

#### 创新点 3：Maven 依赖安全智能扫描
- **结论：技术可行但创新性偏弱，建议降权：定位为"完整性加分项"，校赛不实现，省赛做基础版。**
- 技术路径可行：解析 `pom.xml` / 依赖树（Maven Model API）→ 查询 OSV.dev（免费、无需 Key）或 NVD → 匹配 CVE。
- **风险**：OWASP Dependency-Check、Dependabot、Snyk 已成熟。应答口径："本工具并非漏洞库产品，而是将**供应链安全纳入统一的代码评审报告**，开发者可在同一面板查看代码缺陷与依赖风险。"
- **调整建议**：省赛 W2 实现最小可用版本（解析 + 查询 + 面板展示），投入不超过 3 人日。

#### 创新点 4："评审 — 解释 — 修复"一键闭环
- **结论：可行，演示效果最佳，必做（校赛 1 类，省赛全覆盖）。**
- 技术路径：IDEA QuickFix / IntentionAction 原生支持编辑器联动；LLM 生成修复补丁。
- **风险与对策**：
  - LLM 补丁存在编译失败风险 → 应用前用 PSI 重新解析校验语法，失败则降级为"修复建议文本"；
  - 补丁需人工确认 → 强制 Diff 预览 + 用户确认后应用，支持 Ctrl+Z 回滚；
  - 范围控制 → 校赛仅对"局部可修复"类问题生成补丁（如缺 `rollbackFor`、未使用变量），不做大范围重构。

### 3.2 调整结论

**四项创新点方向全部成立，不做推翻。需三处调整：**

1. **分级落地**：校赛 = 创新点 1（完整演示）+ 2（1 条规则）+ 4（1 类修复）；创新点 3 与其余扩展全部放省赛。**5 天周期无法承载全量范围，必须分级收敛。**
2. **创新点 1 补强融合机制叙事**（双向增强 + 量化数据），避免被评为"简单组合"。
3. **将"证据链"与"量化对比实验"作为独立支撑**：前者应对大模型幻觉质疑，后者应对"已有工具"质疑。

**答辩主线（全场围绕此展开）**：

> 一段 Spring 业务代码提交前 → 规则引擎秒级发现确定性问题 → 大模型解释语义问题并复核规则误报 → 每条意见附带"问题行 + 原因"证据链 → 对事务失效问题一键修复：补丁自动生成、Diff 预览、应用后编译通过。
> **一句话定位：不做"又一个代码助手"，而是"结构级精度的企业级代码评审流水线"。**

### 4.2 统一缺陷模型 IssueModel（并行开发基础，今晚必须冻结）

`IssueModel` 为三个模块之间**唯一**的接口契约。葛佩娴今晚创建该类的骨架（字段见下），20:30 语音对齐时三人共同确认并冻结；冻结后不得私自修改，变更须三人同步。

```json
{
  "id": "唯一ID（引擎生成）",
  "source": "RULE | LLM",              // 来源：规则引擎 / 大模型
  "ruleId": "TransactionRollbackFor",   // 规则编号或 LLM 问题类别
  "severity": "CRITICAL | MAJOR | MINOR",// 严重级别
  "filePath": "全局文件路径",
  "startLine": 42,                       // 1-based
  "endLine": 42,
  "message": "一句话问题描述",
  "evidence": "证据链：为什么是问题（如：受检异常 IOException 未配置 rollbackFor，事务不会回滚）",
  "fixable": true,                       // 是否支持一键修复
  "fixPatch": "（可选）替换后的代码片段或 unified diff"
}
```
